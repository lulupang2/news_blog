### eBPF 코드 프로파일링하기
eBPF 코드를 돌리거나 작성할 때, 그 퍼フォ먼스 영향을 측정하고 싶음. 이 포스트에서는 어떻게하면 그 퍼포먼스 영향을 측정할 수 있는지에 대해 설명할 거임.

#### 본문
우리가 할 건 파일 오픈 오퍼레이션의 퍼포먼스를 측정하는 거야. 우리가 쓰는 코드는 파일 오픈 훅을 사용하는데, 이 훅이 퍼포먼스에 미치는 영향이 얼마나 되는지 확인하고 싶어. 

그럼 어떻게 확인할 수 있을까? 그럼 간단한 C 테스트 하네스를 사용할 거임. 우리가 확인하고 싶은 건 파일 오픈의 퍼포먼스임. 
```c
#define _GNU_SOURCE 
#include <fcntl.h> 
#include <stdio.h> 
#include <time.h> 
#include <stdint.h> 
#include <stdlib.h> 
#include <unistd.h> 
#include <sched.h> 
#include <sys/mman.h> 
#include <sys/syscall.h>
// 코드 생략
```
이 코드는 파일을 연 뒤, 그 시간을 측정해서 파일을 여는데 얼마나 시간이 걸렸는지 측정할 수 있어. 이 코드를 사용하면, eBPF 훅이 붙기 전과 붙은 후의 퍼포먼스 차이를 확인할 수 있을 거임.

### perf 툴 설정
이제 이 코드를 사용해본 결과를 분석하려면, perf 툴을 설정해야 해. 그럼 어떻게 설정할 수 있을까? 
```bash
sudo sysctl -w net.core.bpf_jit_enable=1 
sudo sysctl -w net.core.bpf_jit_kallsyms=1
```
이 명령어들은 JIT를 활성화하고, JIT 컴파일된 BPF 심볼을 노출함으로써, perf 리포트에서 프로그램 이름 대신 알 수 없는 주소가 표시되지 않도록 해주는 거임.

이제 이 설정이 제대로 작동하는지 확인해봐야겠지? 확인하는 법은 간단해. 
```bash
sudo bpftool prog show | rg -A4 ' lsm ' 
sudo rg 'bpf_prog_[0-9a-f]+_ '/proc/kallsyms | rg 'security|path|file|open'
```
이 명령어들은 우리가 측정하고 있는 LSM 훅이 실제로 심볼이 나타나는지 확인해줘.

### 측정 시작
이제 모든 준비가 끝났음. 그럼 퍼포먼스를 측정할 수 있는 코드를 돌려보고, 퍼포먼스를 분석해봅시다.
```bash
sudo taskset -c 3 chrt -f 99 ./bench /etc/hostname 100000 > /tmp/samples.txt 
```
이 명령어는 우리가 만든 테스트 코드를 실행하고, 그 결과를 파일에 저장하는 거야.

이제 이 파일의 결과를 분석해봐야겠지? 분석하는 법은 간단해. 
```bash
sudo $PERF report -i ~/perf.data --stdio --sort comm,dso,symbol > perf.txt
```
이 명령어들은 perf 데이터를 분석해서, 어느 부분에서 퍼포먼스가 낮은지 확인할 수 있게 해줌.

#### 결과
결과는 이렇게 나온다. 
```
| | | | | | |–90.52%–do_dentry_open | 
| | | | | | | | | | | | | --89.78%–bpf_lsm_file_open | 
// 내용 생략
```
이 결과는 퍼포먼스가 낮은 부분이 어디인지 알려줌. 
이 코드는 eBPF 훅의 퍼포먼스를 측정하는 법을 보여줌. 퍼포먼스를 측정하기 위해서는, C 테스트 하네스를 사용하고, perf 툴을 사용해서 코드를 분석해야 함. 이 방법을 사용하면, 퍼포먼스가 낮은 코드 부분을 찾을 수 있고, 최적화를 할 수 있어.
