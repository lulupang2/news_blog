# DuckDB Parquet 파일 페이징은 file_row_number로 하셈
   대용량 پار퀘트 파일에서 한 번에 20만 행씩 보내는 서비스가 있었음. 그런데 API 응답의 최대 크기가 제한되어 있으니까 페이징해야 하는데, 그 방법을 찾아보다가 발견한 게 LIMIT/OFFSET와 file_row_number임. LIMIT/OFFSET는 그냥 일반적인 페이징 방법인데, OFFSET이 19000000 같은 큰 숫자가 되면 그 앞의 행들을 모두 세야 하니까 속도가 개박살남.
   근데 DuckDB에 file_row_number 옵션이 있어서 행의 물리적 위치를 알 수 있어서 행 범위를 지정하는 방식으로 페이징할 수 있음. 
   ### file_row_number의 비밀
   file_row_number를 사용해서 페이징하면 LIMIT/OFFSET보다 2.53배 빠르다는 결과가 나왔음. 그리고 이는 OFFSET이 제대로 작동하는지 테스트해본 결과로, OFFSET은 LIMIT/OFFSET을 사용하면 쿼리가 느려진다고 생각했었지만 실제로는 그렇지 않다는 게 밝혀짐. 
   OFFSET은 file_row_number를 사용하여 row group 단위로 건너뛸 수 있어서 속도가 개월령 안 빠르지만, OFFSET보다 file_row_number를 직접 사용하는 방식이 더 빠르다는 거임.
   ### Row Group
   Parquet 파일은 Row Group이라는 블록 단위로 구성되는데, DuckDB는 file_row_number를 사용하여 Row Group 단위로 건너뛸 수 있어서 속도 개선에 기여함. Row Group이 하나라면 건너뛸 수 없으니까 파일의 Row Group 수를 확인해야 함. 한 번에 보내는 행 수가 100만 행인 것을 넘기면 오프셋 방식이 쓰이질 않음. 
   ### 문제점
   LIMIT/OFFSET을 사용할 때 ORDER BY가 없으면 행의 순서가 보장되지 않아서 중간에 데이터가 손상될 수 있음. 그래서 OFFSET대신 file_row_number를 사용하는 게 훨씬 낫다 임.
