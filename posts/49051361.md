### 클라우드 5세대 모델을 위한 새로운 컨텍스트 엔지니어링 규칙

클라우드 코드의 시스템 프롬프트에서 80% 이상을 제거했어. 클라우드 코드와 자체 에이전트에서 컨텍스트 엔지니어링을 적용하는 법을 알아보자. 

일단 클라우드 코드로 메시지를 보낼 때, 프롬프트는 전체 컨텍스트의 일부분만이야. 대부분의 컨텍스트는 시스템 프롬프트, 스킬, CLAUDE.md 파일, 메모리 등에서 구성됨. 이를 컨텍스트 엔지니어링이라고 부르며, 결과에 큰 영향을 미쳐.

프롬프트와 달리 컨텍스트는 여러 요청에 걸쳐서 사용되기 때문에 특정할 수 없지. 클라우드에 대한 일반적인 프롬프트와 가イ도드를 어떻게 만드는 거냐하면, 유저의 프롬프트가 어떤 건지 모르는 경우 이게 생각보다 꽤 어려울 수 있음. 클라우드의 능력이 발전하면서 이 규칙이 변경되기도 해.최근 클라우드 5세대 모델이 나오면서 시스템 프롬프트에서 80% 이상을 제거했어. 클라우드 코드의 시스템 프롬프트와 CLAUDE.md 파일, 스킬을 업데이트 하는 방법을 알아보자.

클라우드 언호블링

클라우드 코드를 너무 제한했어. 시스템 프롬프트와 CLAUDE.md 파일, 스킬에서 클ラ우드가 이해하기 어려운 메시지를 많이 넣었나 봐. 클라우드 내부에서 클라우드 코드를 사용하는 기록을 보면, 시스템 프롬프트와 스킬, 유저 요청이 서로 충돌하는 경우가 많아. 일반적으로 클라우드는 유저의 의도를 이해해서 올바른 결과를 얻어내지만, 클라우드는 이러한 중복되고 충돌하는 메시지를 더 신중하게 생각해야 해.

이전에는 이런 제약이 필요했지만, 이제는 많은 경우에 이를 삭제하고 모델이 주변 컨텍스트와 판단력을 사용하도록 할 수 있어. 클라우드 코드에는 더 많은 도구가 추가되어. 클라우드는 이전에는 CLAUDE.md 파일을 주요 메모리와 정보의 출처로 사용했지만, 이제는 메모리, 아티팩트, 스킬 등을 사용해서 세션 간에 컨텍스트를 로딩하고 공유할 수 있어.

테나이즈

이전에는 컨텍스트 엔지니어링에 대한 몇 가지 규칙이 있었어. 하지만 이제는 이러한 규칙이 미신이 된 거 같아. 예를 들면, 이전에는 클라우드에게 규칙을 줬지만, 이제는 클라우드가 판단력을 사용하도록 해. 클라우드 코드를 처음 론칭했을 때, 클라우드가 최악의 경우를 피할 수 있도록 강력한 가イ도드를 주었어. 예를 들어, 시스템 프롬프트에 이렇게 말했다고 해봐. 코드에선 주석을 기본적으로 작성하지 않도록 하고, 여러 줄의 주석이나 다중行 블록은 작성하지 말라고. แต 어떤 경우에는 이런 가イ도드가 잘못된 경우가 있었어. 문서화의 경우, 유저에는 자기만의 선호도가 있을 수 있고, 코드의 일부분은 여러 줄의 주석 블록이 필요할 수도 있어.

이전 모델에서는 이런 가イ도드 없이 클라우드가 주석을 잘못 작성하는 경우가 많았어. 하지만 새로운 모델은 더 나은 판단력을 가지고 있어서 이런 규칙 없이도 잘 작동해. 시스템 프롬프트에서 이제는 이렇게 말해. 주변 코드와 읽기 좋은 코드를 작성해: 주석의 밀도, 이름, 관용구를 일치시켜.

이전에는 클라우드에게 예를 보여줬지만, 이제는 인터페이스를 설계해. 이전에는 클라우드에게 도구를 사용하는 방법에 대한 예를 많이 줬어. 하지만 새로운 모델에서는 이런 예가 클라우드를 특정한 탐색 공간으로 제한할 수 있어. 대신에, 도구와 스크립트, 파일의 설계를 생각해봐. 클라우드에게 어떤 매개변수를 주었는지, 어떻게 더 발현적으로 만들 수 있는지 생각해봐. 예를 들어, Todo 도구에서 상태를 pending, in_progress, completed 등으로 나열하면, 클라우드에게 어떻게 사용해야 하는지 힌트를 주는 거지.

이전에는 모든 걸 처음부터 넣었지만, 이제는 점진적인 노출을 사용해. 클라우드 코드가 초기에 코드 리뷰와 버그 체크를 위해 시스템 프롬프트에詳細한 정보를 포함했어. 하지만 이제는 클라우드 코드가 점진적인 노출을 사용해서 올바른 컨텍스트를 올바른 시기에 로딩할 수 있어. 예를 들어, 버그 체크와 코드 리뷰를 스킬로 분리해서 클라우드 코드가 선택적으로 호출할 수 있게 해줬어.

점진적인 노출은 스킬뿐만 아니라 도구에도 적용되어. 일부 도구는 '지연 로딩'으로, 에이전트가 ToolSearch를 사용해서 전체 정의를 찾기 전에 사용할 수 없어. 이렇게 하면 필요할 때만 컨텍스트를 로딩할 수 있어.

同じ 방식으로 CLAUDE.md와 스킬 파일도 사용해. 많은 경우에, 이러한 파일을 모든 알려진 관행을 포함하는 중앙 저장소로 유지하고 싶어할 수 있지만, 필요할 때만 로딩할 수 있도록 파일을 나누는게 더 좋을 수 있어.

이전에는 반복했지만, 이제는単純한 도구 설명을 사용해. 이전 모델에서는 반복적인 지침이나 컨텍스트 창의 끝부분에 있는 지침을 더 잘 따른다고 해. 시스템 프롬프트에 도구에 대한 설명을 추가로 넣었어. 하지만 이제는 이런 반복적인 예를 삭제하고 도구 설명에 지침을 넣어.

이전에는 CLAUDE.md 파일에 메모리를 저장했지만, 이제는 자동 메모리를 사용해. 이전에는 # 핫키를 사용해서 CLAUDE.md 파일에 자동으로 작성했었어.하지만 클라우드가 자동으로 관련된 메모리를 저장하도록 업데이트 됐어.

이전에는 단순한 스펙을 사용했지만, 이제는 풍부한 참조를 사용해. 클라우드 코드에서 kế hoạch 모드에서 마크다운 파일을 사용했었어. 이러한 파일을 계획으로 저장하면 클라우드가 필요할 때 참조할 수 있었지. 하지만 클라우드는 더 복잡한 참조를 처리할 수 있게 됐어. 단순한 마크다운 파일 대신에 HTML 아티팩트를 생성하는 새로운 아티팩트 기능을 사용할 수 있어. 또한 코드를 통해 참조를 제공할 수 있어. 스펙은 다른 코드베이스의 함수나详细한 테스트 세트가 될 수 있어. 룹릭은 클라우드가 특정 분야에서 좋은 디자인을 이해하도록 동적으로 워크플ロー와 VERIFY 에이전트를 생성하도록 해줄 수 있어.

컨텍스트 적용하기

이 모든 걸 모아서, 컨텍스트를 어떻게 조립해야 하냐하면, 시스템 프롬프트, CLAUDE.md 파일, 스킬 등등을 업데이트 해야해. 시스템 프롬프트는 제품 컨텍스트에 크게 연관되어. 클라우드가 어떤 제품인지, 무엇을 하는지 알려줘. CLAUDE.md 파일은 가볍게 유지하고 코드베이스에 대한 간단한 설명을 넣어. 하지만 토큰의 대부분을 코드베이스의 gotcha에 사용해. 예를 들어, 코드를 tổ chức해서 특정 파일에만 타입을 저장할 수 있는데, 그런 경우에는 CLAUDE.md 파일에 설명을 넣어. 

명확한 것들을 클라우드가 파일 시스템이나 저장소에서 알 수 있는 것은 생략해. 점진적인 노출을 많이 사용해. 예를 들어, 작업을 확인하는_unique한 지침이 여러 개 있는 경우, 확인 스킬을 생성해서 CLAUDE.md 파일에서 참조해. 스킬은 클라우드가 필요할 때 정보를 찾을 수 있도록 가벼운 가이드로 작동해야 해. 너무 제한적인 스킬은避해야 해. 긴 스킬은 점진적인 노출을 사용해서 여러 파일로 나눌 수 있어.

스킬은 PARTICULAR한 의견, 지식, 또는 가장 좋은 관행을 포함하기 좋음. 참조는 @mentions를 사용해서 포함할 수 있어. 참조는 클라우드가 계획에 대한 심도있는 정보를 참조할 수 있도록 해줘. 이렇게 하면 클라우드가 더 나은 결과를 얻을 수 있지.

단純化하기

시스템 프롬프트, 스킬, CLAUDE.md 파일 전체에서 단純化가 필요할 수도 있어. 클라우드 닥터라는 새로운 명령어가 나오았는데, 이것을 사용해서 자동으로 단純화할 수 있지. 더 많은 정보는 Fable 필드 가이드에서 볼 수 있어.
