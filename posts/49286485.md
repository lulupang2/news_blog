### 쿠버네티스에서 옥사이드 사용하기: 고객들의 니즈가 우리에게 통합을 가르쳐주었다
쿠버네티스와 옥사이드는 천생연분이야. 쿠버네티스는 인프라스트럭처의 행동을 표준 확장 지점을 통해 정의하고, 옥사이드는 해당 행동을 구현하는데 필요한 원시적인 것들을 API를 통해 노출해줘.integration의 기본은 이미 다 갖춰진 상황이었으니까. 문제는 소프트웨어와 실제로 고객들이 어떤 통합을 benötig하는지 이해하는 것이었어.

이 상황에서 나의 역할은 솔루션 소프트웨어 엔지니어로, 첫 업무는 옥사이드에서 쿠버네티스를 배포하고 운영하기 쉽게 만들어주는 거였어. 첫 업무를 시작하면서 두 가지 리소스를 얻었어. 하나는 고객이 제출한 랜처 노드 드라이버를 위한 풀 리퀘스트고, 또 하나는 초기 RFD 493_initial_k8s_integrations 초안이야.

이 두 가지 리소스로부터 시작해서 팀들의 노력과 고객들의 피드백 루프를 거치면서 더 많은 통합들이 생겨났어.abstract한 설계가 아니라 고객들이 gặp는 문제들에 따라서 통합들을 구축했어. 클러스터 프로비저닝 과정부터 운영 과정까지, 각 단계에서 고객들의 워크플로우가 다음 문제를 드러내었고, 그것이 우리가 구축하는 통합과 앞으로 해야할 플랫폼 작업을形造했다고 할 수 있어.

**쿠버네티스 클러스터 프로비저닝하기**
첫 번째 문제를 해결하려면 쿠버네티스 클러스터를 프로비저닝 하는 방법을 알아야 했어. 랜처 노드 드라이버를 고객이 제출해준_use case를 해결하는 것이 첫 목표였어. 그 Use case를 통해 클러스터를 직접 생성하면서 문제를解决하는 방법을 배우고, 다음 문제를 해결할 수 있는 발판을 만들었어.

단 하나의 프로비저닝 어프로치가 모든 고객의 워크플로우에 적합하지 않아서, 결국 3가지의 통합들을 공개하게 되었어.

*   **랜처 노드 드라이버**: 랜처 노드 드라이버는 실행 가능한 플러그인이야. 랜처가 특정 인프라스트럭처 플랫폼에서 가상머신을 생성하고 관리하는 방법을 가르쳐주는 역할을 해. 옥사이드 랜처 노드 드라이버는 랜처의 동작들을 옥사이드 API 요청으로 변환시켜. 랜처에 설치해서 사용할 수 있으면, 고객들이 옥사이드 인스턴스를 랜처에서 관리하는 쿠버네티스 클러스터의 노드로 프로비저닝 할 수 있게 돼.
*   **오므니 인프라 프로바이더**: 고객들이 사이데로 랩스의 오므니를 사용해서 탈로스 리눅스를 실행하는 쿠버네티스 클러스터를 프로비저닝 하는데 관심을 보였어. 오므니는 인프라 플랫폼에 연결하기 위해 인프라 프로バイ더를 사용하는데, 탈로스 리눅스 인스턴스를 생성하고 오므니에 등록해주는 프로그램들을 사용해. 쿠보컨 북 아메리카 2025가 몇 달 앞으로 다가오면서, 사이데로 랩스와 협력해서 오므니를 위한 옥사이드 인프라 프로바이더를 구축해서展示하는 기회를 잡았어. 또 다른 프로비저닝 플랫폼을 구축해서, 옥사이드의 API를 테스트하는 데도 도움이 되었어.
*   **클러스터 API 프로바이더**: 클러스터 API 프로바이더는 우리의 첫 두개의 통합의 장단점을 보완해서, 업스트림 API를 제공해주면서, 랜처나 오므니 gibi 써드파티 플랫폼 없이 클러스터를 관리할 수 있는 거시야. 클러스터 API를 사용하면, declarative한 방식으로 클러스터를 생성하고, scale하고, upgrade하고, 삭제할 수 있고, 인프라 프로바이더는 플랫폼 특정한 작업들을 처리해줘. 클러스터 API 프로바이더를 구축하는 것은 상당한 투자야. 고객들의 요구와 엔지니어링 용량이 없어서, 프로젝트를 연기했어. 하지만, 나중에 고객들이 더 많이 요청했고, 솔루션 소프트웨어 엔지니어링 팀이 성장하면서, 내 동료 Josh와 Brandon이 프로젝트를 맡아서 클러스터 API 프로바이더 옥사이드(CAPOx)를 출시해서, 고객들이 쿠버네티스 네이티브 방식으로 옥사이드에서 클러스터를 프로비저닝할 수 있게 해줬어.

### 옥사이드 인스턴스 트래킹하기
프로비저닝 통합이 인스턴스를 생성하고 관리하지만, 그것을 쿠버네티스 노드 오브젝트와 reconcile하지는 않아. reconcile하지 않으면 클러스터가 임시로 사용할 수 없는지, 아니면 백킹 옥사이드 인스턴스가 삭제된 건지 구분할 수 없어서, 클러스터가 노드를 초기화하고 안전하게删除할 수 있는 정보를 결코 얻을 수 없어.

이 문제 해결 위해서는, 클러스터에 running하는 구성 요소가 필요해. 구성 요소는 옥사이드 API와 통신하고, 계속해서 옥사이드 인프라와 쿠버네티스 상태를 reconcile해줘야 해. 이걸 위해 쿠버네티스에서 표준 확장 지점을 제공해주는 클라우드 컨트롤러 매니저(CCM)를 만들었어. CCM은 인프라 특정 컨트롤러们이 쿠버네티스 리소스들을 인프라 프로바이더의 API와 통합할 수 있게 해줘. 인프라 특정 코드를 쿠버네티스에 추가하지 않고서도 말이야.

옥사이드 클라우드 컨트롤러 매니저를 만들어서, 쿠버네티스와 옥사이드를 연결했어. 노드 컨트롤러는 쿠버네티스 노드 오브젝트를 백킹 옥사이드 인스턴스와同步시켜주고, 인스턴스 ID, 네트워크 어드레스 등 정보를 기록하고, 인스턴스가 running 중인지, 종료되었는지, 삭제되었는지 등을 보고 해줘. 쿠버네티스는 이 정보를 사용해서 노드를 초기화하고, 백킹 인스턴스가 삭제되면 안전하게 삭제해줘.

클라우드 컨트롤러 매니저는 인스턴스를 생성하거나 클러스터를 프로비저닝하지는 않아. 랜처 노드 드라이버나 오므니 인프라 프로바이더, CAPOx 같이 프로비저닝 통합의 역할을 해. 대신에, 런타임 통합을 제공하면서, 클러스터 안에서 새로운 인프라 어웨어 컨트롤러들을 쉽게 추가할 수 있게 해줘.

클라우드 컨트롤러 매니저가 있으면, 다음 문제인 로드 밸런서 서비스를 사용하는 방법을 해결할 수 있을 것 같아.
 
### 로드 밸런서 서비스 사용하기
클라우드와 통합된 쿠버네티스에서 기대하는 기능 중 하나가 로드 밸런서 서비스 지원이야. 유저가 로드 밸런서 서비스를 생성하면, 쿠버네티스는 클라우드 프로바이더의 서비스 컨트롤러에게 필요한 인프라를 프로비저닝하고, 서비스 상태에 어드레스를 publish하도록 해. 하지만, 옥사이드에는 네이티브 로드 밸런서가 없다는 문제가 있었어.

 옥사이드에는 플로팅 IP가 있었어. 플로팅 IP는 랙의 외부 IP 풀에서 할당된 어드레스야. 이 어드레스를 인스턴스에 붙이면 detach할 수 있所以, 인스턴스를 VPC 밖에서 접근할 수 있게 해줘. 플로팅 IP를 사용해서 로드 밸런서 서비스를 사용할 수 있게 할 수 있었어. 플로팅 IP를 사용해서 트래픽을 받으면, 쿠버네티스 서비스 데이터플레인이 트래픽을 적절한 포드에 분산시켜줘.

이 방법이 작동하려면, 옥사이드 플로팅 IP가 인스턴스에 어떻게 보이는지에 대한 고려가 필요해. 플로팅 IP는 인스턴스에 прозрач해. 첫 번째로, 옥사이드는 인바운드 트래픽의 目的地 어드레스를 인스턴스의 내부 IP로 변환해서 인스턴스로 보낸어. 두 번째로, 인스턴스는 플로팅 IP로 설정된 네트워크 인터페이스를 가지지 않아.
